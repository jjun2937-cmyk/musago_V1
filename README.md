# musago_V1 — 무사고전환 데이터/레이아웃 산출 자동화

무사고 전환 판매플랜 관련 계약 데이터에서, 조건별 계약 건수를 집계하는 엑셀 업무를
파이썬 스크립트로 재현 가능하게 만든 작업입니다.

이 저장소는 여러 차례 지표 정의를 다시 잡으며 반복 개발되었습니다 (아래 "버전
히스토리" 참고). **지금 실제로 쓸 것은 최종 버전(v6) 하나뿐**이며, 다음 섹션에
사용법이 있습니다. v1~v5는 그 이전까지의 개발 과정 기록으로 남겨둔 것입니다.

## 최종 버전 사용법 — `scripts/run_pipeline_v6.py`

데이터 시트(수금부문명 헤더 보유), 매핑정보 시트(`*무사고기간` 헤더 보유),
최대전환매핑 시트(`최대전환년수` 헤더 보유), 이렇게 3개 시트가 든 엑셀 파일
하나만 주면, 아래 3단계를 자동으로 실행해서 "데이터 파일"과 "보고 파일"을
만들어주는 통합 실행기입니다.

```bash
# 필요 패키지: pip install openpyxl
# 필요 프로그램: LibreOffice (soffice)
#   Ubuntu/Debian: sudo apt-get install libreoffice-calc
#   macOS:         brew install --cask libreoffice

python scripts/run_pipeline_v6.py <입력.xlsx> <데이터출력.xlsx> <보고출력.xlsx>
```

내부적으로 하는 일:
1. **`build_report_v6.py`** — 입력 파일에서 데이터/매핑정보/최대전환매핑 시트를
   자동 식별하고, 경과전환판매플랜코드(매핑 실패 시 최대전환매핑으로 폴백)·
   전환여부·최대전환플랜코드·년수비교 등을 채운 뒤, 세부보고/합산보고 ×
   부문별/상품별 레이아웃을 월별 블록으로 수식 생성
2. **`recalc_util.py`** — LibreOffice headless로 전체 수식을 재계산 (openpyxl은
   계산된 값을 캐시하지 않으므로 필수 단계). 수식 오류가 있으면 셀 목록을 출력
3. **`split_report_v6.py`** — 원본 데이터가 든 무거운 "데이터 파일"과, 레이아웃
   4종만 값으로 담은 가벼운 "보고 파일"로 분리해서 저장한 뒤, 분리 과정에서
   지워지는 데이터 파일 쪽 수식 캐시값을 복원하기 위해 데이터 파일을 한 번 더
   재계산

옵션: `--timeout 초`(기본 900, 데이터가 많으면 늘릴 것), `--keep-combined`(중간
결합 파일을 안 지우고 남겨서 디버깅용으로 확인 가능)

### 지표 정의와 산출물 구조는 아래 "v6" 섹션에 자세히 정리되어 있습니다.

## 버전 히스토리

### v1 — `fill_data_sheet_formulas.py` / `fill_layout_formulas.py`

가장 처음 버전. 시트명/컬럼 위치가 고정된 하나의 실제 파일을 대상으로,
`업무정의` 시트에 적힌 규칙을 그대로 수식으로 구현했다.

```bash
python scripts/fill_data_sheet_formulas.py <원본.xlsx> <중간.xlsx>
python scripts/fill_layout_formulas.py <중간.xlsx> <최종.xlsx>
```

#### 데이터 시트 (T/W/X/Y/Z열)

| 열 | 정의 |
|---|---|
| T (사고전환판매플랜코드) | `최초판매플랜코드(K) & 무사고년수(S)`를 키값으로 매핑정보 시트 E열에서 찾아 F열 값을 반환 |
| W | 현재판매플랜코드(E) = 경과전환판매플랜코드(M) 여부 |
| X | 현재판매플랜코드(E) = 사고전환판매플랜코드(T) 여부 |
| Y | 경과년수(L) = 무사고년수(S) 여부 |
| Z | `V(사고구분코드)가 '01'/'02'가 아니고 Y=FALSE이면서 (X=TRUE 또는 W=TRUE)`이면 `'기전환'`, 아니면 공란 |

#### 결과레이아웃 시트 (개념상 A~I, 실제 시트열 B,C,D,E,F,G,H,I,K)

| 개념 | 실제열 | 정의 |
|---|---|---|
| A 전체계약건수 | B | 수금부문(개인/전략/신사업/법인)별 전체 계약 건수 |
| B 사고有 | C | V가 '01' 또는 '02'인 건수 |
| C = A-B | D | (기존 수식) |
| D 기존전환완료 | E | Z='기전환'인 건수 |
| E = C-D | F | (기존 수식) |
| F 기존미전환 | G | V not in(01,02), Z≠'기전환', Y=FALSE 인 건수 |
| G = E-F | H | (기존 수식) |
| H 전환완료 | I | V not in(01,02), Z≠'기전환', Y=TRUE, X=TRUE 인 건수 |
| I = G-H | K | (기존 수식) |
| 현장활동확인 (001~007) | O~U | "I"의 여집합(V not in(01,02), Z≠'기전환', Y=TRUE, X=FALSE) 중 전환처리구분코드별 건수 |

`결과레이아웃`에 이미 있던 D/F/H/K/J/L/N/M/V/W열 등의 수식은 그대로 두었고,
하드코딩된 0이 들어있던 B/C/E/G/I/O~U열에만 위 규칙대로 수식을 채웠습니다.

레이아웃에는 4개 월 블록(26.4월/23.5월/23.6월/23.7월)이 있는데, 데이터 시트가
단일 월(계약체결월 전부 '06') 자료라서 **첫 블록(6~9행)만** 이번 데이터로 채웠고
나머지 3개 블록은 대응하는 원본 데이터가 없어 건드리지 않았습니다.

#### 주의: 엑셀 COUNTIFS 조건문자열의 숫자/텍스트 오인 버그

V열(사고구분코드) 값 `'01'`/`'02'`, U열(전환처리구분코드) 값 `'001'`~`'007'`은
텍스트지만 숫자처럼 보이는 문자열입니다. `COUNTIFS(range, "<>01")`처럼 조건문자열로
비교하면 실제 Excel은 `01`을 숫자 `1`로 해석해버려서, 텍스트 셀은 숫자와 절대
같을 수 없으므로 `<>1` 조건이 모든 행에서 TRUE가 되어(필터가 무력화되어) 잘못된
값이 나옵니다. (재현/검증에 쓰는 LibreOffice는 텍스트로 올바르게 비교하기 때문에
처음에는 이 문제를 놓쳤습니다.)

그래서 V/U열과 비교하는 결과레이아웃의 **C, G, I, O~U열은 `COUNTIFS` 대신
`SUMPRODUCT` 배열비교**로 작성했습니다. `SUMPRODUCT` 안의 `=`/`<>`는 조건문자열
파서를 거치지 않고 셀 값을 있는 그대로 비교하므로 텍스트/숫자 오인 문제가 없습니다.

#### 검증

- 결과레이아웃의 모든 집계값을 원본 데이터에서 순수 파이썬으로 독립 재계산한
  값과 대조하여 일치함을 확인했습니다.
- LibreOffice 재계산 기준 수식 오류 0건 (단, 법인 그룹처럼 계약 건수가 0인 경우
  비율(%) 계산에서 발생하는 `#DIV/0!`는 손대지 않은 기존 비율 수식의 특성이며
  원본 템플릿에도 이미 존재하던 현상입니다).

### v2 — 헤더명 기반 범용 스크립트 (`scripts/build_report.py`)

시트명이나 컬럼 위치가 매번 달라지는 원본 파일에도 대응하도록 일반화한 버전입니다.
이후 데이터는 "데이터 시트"와 "매핑정보 시트" 두 개만 제공되며, `결과레이아웃`은
매번 새로 생성합니다.

```bash
python scripts/build_report.py <입력.xlsx(데이터+매핑정보 두 시트)> <출력.xlsx>
```

#### 동작 방식

1. **시트 자동 식별** — 시트명과 무관하게, 헤더에 `수금부문명`이 있는 시트를
   데이터 시트로, 나머지를 매핑정보 시트로 식별.
2. **헤더명으로 컬럼 탐색** — 컬럼 순서/개수가 달라져도 아래 헤더 텍스트로 위치를
   찾음: 현재판매플랜코드, 최초판매플랜코드, 경과전환판매플랜코드, 경과년수,
   무사고년수, 사고구분코드, 전환처리구분코드, 수금부문명, 계약체결월.
3. **헤더 폴백 규칙** — 위 세 플랜코드 헤더가 없으면:
   - 최초판매플랜코드 → `적용시작일시` 바로 오른쪽 `판매플랜코드` 열
   - 현재판매플랜코드 → `상품명` 바로 오른쪽 `판매플랜코드` 열
   - 경과전환판매플랜코드 → `세부플랜코드` 바로 오른쪽 `전환판매플랜코드` 열

   찾은 열의 헤더는 결과 파일에서 정식 이름으로 바꿔 씁니다.
4. **매핑정보 키값열 자동 생성** — `키값` 헤더가 없으면 새로 추가하고
   `=판매플랜코드&경과년수` 수식으로 채움.
5. **T/W/X/Y/Z 열** — 데이터 시트에 해당 헤더가 있으면 재사용, 없으면 맨 우측에
   새로 추가 (v1과 동일한 로직).
6. **결과레이아웃 동적 생성** — `계약체결월`의 고유값 개수만큼 월 블록을 만들고,
   각 블록은 `수금부문명`에 "개인/전략/신사업/법인" 키워드가 **포함**되는지로
   매칭(`SEARCH`, 대소문자 무관 부분일치)해서 4개 그룹 + 합계 행을 채움
   (예: `개인부문`, `개인사업부문` 모두 "개인" 그룹으로 매칭).
   **총계(합계) 행은 4개 그룹의 합이 아니라 해당 월 전체를 그룹 구분 없이
   독립적으로 재집계**합니다 — 그룹 키워드 어디에도 안 걸리는 수금부문명(예:
   `경영지원실`)이 있어도 총계에서 누락되지 않도록 하기 위함입니다(v2 초판에는
   총계=SUM(4개 그룹)으로 되어 있어 이런 행이 총계에서 빠지는 버그가 있었고,
   실사용 중 발견되어 수정했습니다). 각 블록에는 그룹 매칭에서 빠진 건수를 바로
   보여주는 **"미분류(그룹매칭 안됨)" 행**도 추가되어, 이 값이 0이 아니면 데이터에
   예상 못한 수금부문명이 있다는 뜻입니다.
7. **추천요약 시트 신규 추가** — 월×부문을 한 화면에 정리한 요약표
   (전체계약건수/전환대상/기전환완료/당월전환대상/전환완료/완료율(%)/전환미완료/
   현장활동확인/현장활동미확인), 완료율(%) 열에는 3색 조건부서식 적용.

#### v2로 실제 검증한 사례

(당시 파일명 `result/무사고전환_결과_04-07월.xlsx` — v4에서 파일 분리 방식으로
바뀌면서 이 파일은 지금 저장소에는 없고 아래 v4의 데이터/결과 파일로 대체됨)
시트명이 `Sheet1`/`Sheet2`였고, 데이터
컬럼이 42개(원본 26개 대비 증가)였으며 04~07월 4개월치(134,943행)가 섞여 있던
실제 데이터로 실행한 결과. 위 폴백 규칙이 모두 실제로 발동했고(현재판매플랜코드,
최초판매플랜코드, 경과전환판매플랜코드 헤더가 실제로 없었음), 수금부문명도
`개인사업부문/전략사업부문/신사업부문/법인사업부문`으로 되어 있어 포함-매칭이
실제로 필요했습니다. 06월 데이터에 그룹 키워드 어디에도 안 걸리는 `경영지원실`
1건이 있어 총계 행 버그(위 6번 항목)가 이 실행에서 실제로 드러났고, 수정 후
재검증했습니다. LibreOffice 재계산 기준 수식 오류 0건(679,683개 수식), 총계행
포함 독립 파이썬 재계산과 04~07월 전체(총계 4개 + 그룹 16개 + 미분류 4개) 완전
일치 확인.

**참고**: 이 결과를 검증할 때 이전 결과물인 `result/무사고전환_데이터_결과.xlsx`
(단일 월 데이터 기반)의 06월 값과 직접 비교해보려 했으나, 두 파일의 증권번호를
대조한 결과 **겹치는 계약이 0건**이었습니다(증권번호 대역 자체가 다름). 즉 두
파일은 같은 06월 데이터가 아니라 서로 다른 표본이라 값을 1:1로 대조하는 검증은
의미가 없고, 대신 각 파일 내에서 원본 데이터 → 순수 파이썬 재계산 → 시트 수식
값이 일치하는지로 검증했습니다.

### v4 — 지표 정의 재설계 + 데이터/결과 파일 분리 (`scripts/build_report_v4.py`)

v2의 T/W/X/Y/Z(경과년수=무사고년수 비교) 기반 지표를 폐기하고, "무사고전환은
사고구분코드가 아니라 실제 판매플랜코드로 역추적해야 한다"는 논의 끝에 아래
지표로 완전히 새로 설계했습니다.

#### 핵심 전제

- **무사고년수 필드는 실시간이 아니다.** 그래서 `경과년수 ≠ 무사고년수`로 보여도
  실제로는 같을 수 있고, 이 경우 판단은 코드 일치 여부로 역추적한다.
- 전환은 오직 무사고년수만큼만 가능하다 (별도의 "정상승급 트랙"은 없음).
- **사고구분코드('01'=당사사고 / '02'=타사사고)** 자체도 "이번 사이클"에만 찍히는
  값이라, 과거 사고 이력 전체를 대변하지 않는다 (경과년수>무사고년수인 계약의
  78%가 사고구분코드는 공백).

#### 지표 정의

| 항목 | 정의 |
|---|---|
| 유지계약(A) | 그룹별 전체 계약 건수 |
| 사고有(당사)(B) | 사고구분코드='01' **이면서** 현재판매플랜코드 ≠ 경과전환판매플랜코드 (01이어도 이미 경과전환판매플랜코드로 올라와 있으면 여기서 빠지고 당월전환완료로 편입) |
| 당월전환대상 | 유지계약 − 사고有(당사) |
| 당월전환완료 | **현재판매플랜코드 = 경과전환판매플랜코드**인 계약 전체 (사고구분코드 무관 — 무사고년수 필드가 스테일이라도 플랜이 이미 경과전환판매플랜코드와 같다면 그 시점엔 실제로 무사고였다고 역추적) |
| 당월전환미완료 | 당월전환대상 − 당월전환완료 (= 전환처리구분코드 001~007로 세분화) |
| 기존전환완료 | 사고有(당사) 중 **현재판매플랜코드 ≠ 최초판매플랜코드** (사고전환판매플랜코드는 무사고년수=0이면 매핑정보에 값이 없어 항상 공란이 되므로, "최초판매플랜코드에서 조금이라도 바뀌었는지"로 전환 여부를 판단) |
| 기존전환미완료 | 사고有(당사) − 기존전환완료 (= 전환처리구분코드 001~007로 세분화) |

#### 파일 분리

한 파일에 원본 데이터(13만 행)와 레이아웃을 같이 담으면 20MB가 넘어가서,
**데이터 파일**(데이터 시트 + 매핑정보, 수식 유지)과 **결과 파일**(레이아웃
4종만, 값으로 고정)을 분리했습니다. 레이아웃의 SUMPRODUCT 수식이 데이터 시트를
참조하기 때문에, 결과 파일에는 데이터 시트가 없어 수식을 그대로 옮기면 `#REF!`가
납니다. 그래서 순서를 이렇게 잡았습니다:

```bash
python scripts/build_report_v4.py <입력.xlsx> <결합.xlsx>      # 1) 결합 파일 생성(수식)
# LibreOffice로 결합 파일 재계산 (recalc_util.py 또는 엑셀에서 열기)
python scripts/split_report_v4.py <재계산된_결합.xlsx> <데이터.xlsx> <결과.xlsx>  # 2) 분리
```

지금은 이 두 단계 + 재계산을 `scripts/run_pipeline.py` 하나로 묶어서 실행하면
됩니다 (맨 위 "최종 버전 사용법" 참고).

- `result/무사고전환_데이터_04-07월.xlsx` — 데이터 파일 (약 20MB)
- `result/무사고전환_결과레이아웃_04-07월.xlsx` — 결과 파일 (약 35KB, 레이아웃 4종)

  = 192개 셀 그룹) 원본 데이터 → 순수 파이썬 재계산 값과 시트 값이 완전히 일치.

### v5 — "기존" 버킷 게이트 확대 + 원본 템플릿 서식 재현 (`scripts/build_report_v5.py`)

v4를 실사용하며 "당월전환미완료 건수가 너무 많은 것 같다"는 의문에서 출발해
지표를 다시 검증한 결과, v4의 "사고有(당사)" 게이트(`사고구분코드='01'`)가
실제 사고 이력이 있는 계약의 **22%만 잡아내고 있었고**, 나머지 78%(이미
전환 완료된 16,239건 포함)가 전부 "당월전환미완료"로 잘못 편입되고 있었음을
확인했습니다. 원인은 사고구분코드가 "이번 사이클"에만 찍히는 값이라 과거
이력 전체를 대변하지 못한다는 v4에서도 이미 인지했던 한계가, 게이트 자체를
결정하는 데도 그대로 영향을 준 것이었습니다.

#### 바뀐 지표 정의

| 항목 | v4 | v5 |
|---|---|---|
| 사고有(당사) 게이트 | 사고구분코드='01' **이면서** 현재판매플랜코드≠경과전환판매플랜코드 | **경과년수 ≠ 무사고년수**인 계약 전체 (사고구분코드에 더 이상 의존하지 않음) |
| 기존전환완료 | 사고有(당사) 중 현재판매플랜코드 ≠ 최초판매플랜코드 | 위 확대된 게이트(경과년수≠무사고년수) 중 **현재판매플랜코드(E) ≠ 최초판매플랜코드(K)** |
| 기존전환미완료 | 사고有(당사) − 기존전환완료 | 사고有(당사) − 기존전환완료, **전환처리구분코드 001~007로 세분화 추가** (v4는 세분화 없이 합계만) |
| 당월전환완료 | 현재판매플랜코드 = 경과전환판매플랜코드 | 동일 (변경 없음) |

#### 이 과정에서 발견하고 고친 버그 2건

1. **데이터 파일 수식 캐시값 소실 버그** (`split_report_v4.py` → v5에서 수정):
   결합 파일을 `openpyxl.load_workbook(..., data_only=False)`로 열어 레이아웃
   시트만 지우고 다시 저장하면, openpyxl은 남은 수식 셀들의 캐시된 계산값을
   보존하지 못하고 수식 문자열만 남긴 채 값을 전부 비워버립니다. 그 결과
   실제로 배포됐던 "데이터 파일"의 사고전환판매플랜코드(T열)·매핑정보 키값
   열이 100% 공란으로 저장되어 있었습니다. `split_report_v5.py`와
   `run_pipeline.py` 양쪽에 데이터 파일을 저장한 직후 `recalc_util.recalc()`를
   한 번 더 호출해 캐시값을 복원하도록 고쳤습니다.
2. **LibreOffice 재계산 시 폰트 대체 문제**: 원본 글꼴 '맑은 고딕'(Windows
   한글 폰트)이 재계산에 쓰는 Linux 환경에 설치되어 있지 않으면, LibreOffice가
   자체 대체 글꼴(예: WenQuanYi Zen Hei)로 바꿔서 그대로 저장해버립니다.
   `split_report_v5.py`의 `copy_values_only()`에서 `cell.font.copy()` 대신
   `Font(name='맑은 고딕', ...)`로 이름만 강제 재설정하도록 고쳤습니다.

### v6 — 신규 템플릿(사용자 제공) 반영 + 부문별/상품별 이중 그룹 + 01~03월 데이터 (`scripts/build_report_v6.py`)

사용자가 새 템플릿(연차별 COUNTIFS 수식 + "최대전환매핑" 시트 방식)을 직접
가져오면서, 01~03월 실제 데이터로 그 템플릿의 로직을 검증·보완하는 과정에서
지표를 v6로 다시 정리했습니다. v5까지의 "경과년수 vs 무사고년수" 프레임과는
완전히 다른, 연차별 전환구분값 캐스케이드 + 매핑 실패 시 최대전환 폴백이라는
새 프레임입니다.

#### 새로 생긴 개념

- **최대전환매핑**: 전환전 대표플랜코드마다 "최종적으로 도달해야 할 플랜코드"와
  "거기까지 남은 년수(최대전환년수)"를 알려주는 별도 테이블. 원래 매핑테이블
  (전환전플랜+년수→전환후플랜)에서, 같은 전환후플랜이 반복되기 시작하는 첫
  시점(=최대전환년수)만 남기고 그 이후 중복 행은 제거해서 만든다.
- **년수비교** = 최대전환년수 < 경과년수. 즉 "이미 최종목표 도달 시점을 지난"
  계약을 판별하는 플래그. 매핑테이블에서 최대전환년수 이후의 중복 행을
  지우면, 경과년수가 그 이상인 계약은 매핑 조회가 실패(N/A)하므로 **경과전환
  판매플랜코드 계산 시 매핑 실패하면 최대전환매핑의 최대전환플랜코드로
  대체(폴백)한다.**

#### 지표 정의 (연차 1~5, 부문/상품 그룹 공통)

| 항목 | 정의 |
|---|---|
| 대상 | 그룹×연차 전체 건수. **2연차부터는** 이미 최종목표 도달(전환여부=TRUE)하고 그 시점도 지난(년수비교=TRUE) 계약을 제외 |
| 사고유 | 이번 연차 전환구분값=0, 또는 (공백이고 직전연차=0). 단 **이미 전환여부=TRUE로 확인된 건은 사고 기록이 있어도 제외**("사고정보보다 현재 플랜정보가 더 정확하니 사후 검증") — 이번연차 직접사고는 년수비교=FALSE 조건으로, 캐스케이드(직전연차사고)는 년수비교=TRUE 조건으로 제외해 대상 쪽 matured 제외와 이중차감되지 않도록 함 |
| 전환대상 | 대상 − 사고유 |
| 전환완료 | 사고유 여부와 무관하게 전환여부=TRUE & 년수비교=FALSE 전체 (사후검증으로 재편입) |
| 미전환 | 전환대상 − 전환완료 |
| 전환예정 | 이번 연차 전환구분값=1 & 전환여부=FALSE. 단 전환처리구분코드(001~004,007) 있는 건은 코드별 항목과 겹치므로 제외(중복 방지) |
| 코드별(연락두절/사고있음/고객거부/압류계약/ARS거부) | 이번연차=1 또는 (공백, 단 사고유 캐스케이드 케이스는 제외) & 전환여부=FALSE & 코드일치 |
| 미활동 | 미전환 − (전환예정 + 코드별 합계). 뺄셈으로 산출해 예외 케이스까지 자동 흡수 |

발견/수정한 버그:
- **COUNTIFS 숫자/텍스트 오인**: 전환사고구분값1~5, 전환처리구분코드가 텍스트로
  저장돼 있는데 비교값을 따옴표 없는 숫자(`사고1,0`)로 쓰면 LibreOffice에서는
  매칭이 전혀 안 됨(Excel은 관대하게 처리하지만 엔진마다 다름) — 비교값을 전부
  텍스트로 명시(`사고1,"0"`)해서 해결.
- **matured 계약 이중차감**: "대상"은 matured 계약을 빼는데 "사고유"는 안 빼서,
  사고유이면서 동시에 matured인 계약이 전환대상 계산에서 두 번 빠져 미전환이
  실제보다 작아지는 문제 — 사고유 계산에도 matured 제외 조건을 대칭적으로
  추가해서 해결.
- **전환예정 ↔ 코드별 중복 계산**: 전환예정이 코드 조건 없이 "사고=1" 전체를
  세면서 코드별 항목과 겹침 — 전환예정에서 코드별 해당분을 빼서 해결.

#### 그룹 기준 2종 + 산출 파일

- 부문별(수금부문명, 정확매칭 4종: 개인/전략/신사업/법인사업부문)
- 상품별(상품명, 데이터에서 자동 추출한 정확매칭 18종)
- 각 기준마다 **세부보고**(월×그룹×연차, 5개 연차 행 + 그룹별/월별 합계) /
  **합산보고**(월×그룹, 연차 합산 한 줄) 두 시트, 총 4개 레이아웃 시트
- `result/무사고전환_데이터_01-03월.xlsx` — 데이터 파일(원본데이터+매핑정보+
  최대전환매핑+파생컬럼, 수식 유지, 약 16MB)
- `result/무사고전환_보고서_01-03월.xlsx` — 보고 파일(레이아웃 4종 값만, 약 45KB)

**서식/레이아웃**: 처음엔 병합/색상 없이 밋밋하게 만들었다가, 사용자가 보낸
"이런 형태로 안 되냐"는 별도 블랭크 템플릿 파일(세부보고/합산보고 시트에
서식만 있고 값은 비어있는 1~12월용 양식)을 픽셀 단위로 분석해서 완전히
다시 짰다. 실제 반영한 배치:

- **세부보고**: 월 블록 맨 위에 **전사 계**가 오고(부문 3종의 연차별 합계를
  SUM), 그 아래 개인/전략/신사업 순서로 개별 부문 블록이 옴(법인사업부문은
  화면에서 제외 — 전사계 합계에도 포함 안 됨, 즉 존재 자체를 빼는 것으로
  처리). 부문별 컬럼은 "전사 계"만 C:D 두 칸을 합쳐서 쓰고 개별 부문은 D열
  하나만 세로 병합해서 한 칸 들여쓴 것처럼 보이게 함. 월 셀은 그 달 블록
  전체(전사계+부문 전부)에 걸쳐 세로 병합. 헤더(월/부문별/연차/유지계약/...)는
  3행 구조로, 현장활동확인·현장활동미확인은 각각 별도 섹션(전자는 전체比+
  전환예정+코드5종, 후자는 단독 카운트+전체比)이고 헤더는 2개월마다 반복
  (원본 템플릿이 딱 그렇게 되어 있음 — 인쇄 페이지 나누기 흔적으로 보임).
  전사계 블록(합계+연차1~5, 6행 전부)은 테마 accent5+tint0.8 파란색
  (`DAE3F3`)으로 강조, 개별 부문은 "합계" 행 한 줄만 노란색(`FFFF00`)으로
  강조 — 원본 템플릿 색상을 theme1.xml에서 직접 추출해 tint 공식으로 재현.
- **합산보고**: 전사계 행 자체가 없다. 월 구분행(전체 폭 병합, 예: "1월")
  아래 부문별 한 줄씩(개인/전략/신사업, 짧은 표기)만 나열 — 세부보고의 연차
  1~5행을 SUM해서 계산.
- 상품별 레이아웃도 부문별과 동일한 배치를 그대로 적용(상품명은 축약 없이
  원본 코드 그대로 표시).
